# Fulcrum Twin — simulation engine master plan

What it takes to turn the twin from a scene that shows a fulfillment centre into an engine that *runs* one:
what-if scenarios anyone can build, and a live feed the twin renders and reasons from.
This is the build plan for phases 2 and 3 of [PLAN.md](PLAN.md). Task-level progress stays in [TASKS.md](TASKS.md).

Status: draft for your approval, 2026-09-21. Nothing here gets built until a task is picked and approved.

---

## 1. The ask, stated precisely

Two requirements, plus the one that falls out of them:

| # | Requirement | What it means concretely |
|---|---|---|
| 1 | **What-if scenarios** | A person changes something — staffing, demand, layout, a policy — and gets a defensible answer to "what happens?" with a number attached and an error bar, not a vibe. |
| 2 | **Live data** | The twin renders and reasons from a real feed (WMS, scanners, conveyors, labour) instead of a scripted loop. |
| 3 | **Fork from live** *(implied)* | A scenario started from *right now*, not from an empty building. "We're behind and it's 14:20 — if I move six pickers to inbound, do we make the 16:00 carrier cutoff?" This is the feature that makes it a *twin* rather than a simulator, and it is the reason 1 and 2 must be one engine rather than two products. |

**Non-goals** (worth stating so the engine does not balloon): no general-purpose simulation product, no
optimisation solver beyond parameter search, no write-back control of the real FC. The engine reads and
advises. Nothing on this plan moves a physical conveyor.

## 2. Where we are today

Phase 1 built a real facility and a real console. The important thing about it, for this plan: **the scene is
the state.** Every fact lives in a Three.js object and is advanced by the frame loop in `src/main.ts`.

```ts
function frame(now: number) {
  const dt = Math.min(0.05, (now - last) / 1000)   // clamped: time is silently dropped on a hitch
  tour.update(dt); rig.update(dt); building.update(dt); for (const r of rackings) r.update(dt)
  conveyor.update(dt); people.update(dt); trace.update(dt); layers.update(); picker.update()
  renderer.render(scene, rig.camera)
  ui.update(dt, { fps, calls: renderer.info.render.calls, tris: renderer.info.render.triangles })
  requestAnimationFrame(frame)
}
```

Every module takes a bare `dt` and keeps its own accumulator; no absolute sim time is passed anywhere. The
clamp is right for a renderer and wrong for a simulation — the sim needs its own fixed-step accumulator.

That has to invert. A simulation you can interrogate cannot be owned by a renderer — see §3.

### What already exists and what it becomes

| Today | Where | Becomes |
|---|---|---|
| `buildFacility()` returns every entity with world position, size and face; `facility.byId` resolves any location ID | `src/facility.ts`, `src/layout.ts` | The **spatial model** the sim reads. Layout becomes an *input* to a scenario, not a constant. |
| Scripted loops: each picker cycles a fixed `Step[]` plan forever, totes ride a conveyor modulo, doors ease open | `src/scene/*.ts` | **Views.** Each subscribes to sim state and interpolates between events. |
| `Console.log(src, msg, level)` — plain-string events, plus a synthetic generator (`pushEvent`, on a 0.7–2.9 s timer) that invents events from templates and 26 pre-seeded ones at boot | `src/ui.ts`, `index.html` | The **event journal** — structured, versioned, filterable. Same panel, real payloads; the generator switches off. |
| Callback seams: `people.onScan`, `people.onDrop`, `people.onEvent`, `trace.onEvent`, `trace.onDone` | `src/main.ts` | Exactly the hook points the sim takes over. The strangler path starts here. |
| KPI tiles that **random-walk from a fixed seed** (`tickKpis`), and sparklines generated by hashing the entity ID rather than from data | `src/ui.ts`, `index.html` | **Metrics engine** output. Every tile becomes a derived, auditable number. |
| `FEED · LIVE 1.0s`, `ACTIVE ALERTS`, EVENT STREAM filters ALL/WARN+/CRIT | `index.html` | The live-feed and alerting surfaces. Already shaped correctly; they need a real source. |
| `__rngDraws()` — a fingerprint of the whole seeded facility | `src/main.ts` | The **determinism fingerprint** pattern, extended to a KPI fingerprint per run (§4.8). |
| Deep links: `#view=`, `#select=`, `#tour=`, `#flow=walk` | `src/main.ts` | Scenario sharing: `#scenario=peak-staffing&rep=3&t=14:32`. Same mechanism, new keys. |

### What is missing

Phase 1 was honest about this — `PLAN.md` says "metrics are simulated" and `TASKS.md` flags each stub. But the
model has no way to *represent* the things a simulation is made of:

- **No sim clock.** Time exists only as a wall-clock string for the console and per-module `dt` accumulators.
  `lastPick` and `lastReplen` are pre-formatted display strings (`'3 h 12 min ago'`), not timestamps — unusable
  as data.
- **No queues or backlogs.** `Station.queue`, `Dock.progress`, `Slam.rejects`, `PutWall.ordersOpen` and
  `Truck.battery` are seeded random values with **no writer anywhere in the codebase**. Nothing accumulates work.
- **No SKU master.** `sku()` generates an ID per call, so the same product name carries a different SKU at every
  site and no SKU is ever reused. There are no per-SKU dimensions, weight, case pack or velocity class — all of
  which demand modelling and the standards in §4.7 need.
- **No order entity.** `orderId` exists only as a string inside `OrderTrace`. There is no order, no line, no
  work item to schedule — and nothing to hang a due time or a carrier cutoff on.
- **No repaint path.** This is the one that bites. Geometry is baked at construction and **data mutation does not
  repaint**: `bay.fill` is computed once and never recomputed, pallet instances are allocated only for filled
  slots with no delete path, and the inbound, packing, outbound and rebin modules read entity state once in
  their constructors. `Racking.setLayer('inventory')` is the only bulk repaint in the app. A sim that changes
  state must be able to *show* it, so an explicit diff/repaint path is a prerequisite, not polish (15.10).

## 3. The core decision: invert ownership

**The model becomes authoritative, headless and deterministic. The 3D scene becomes a projection of it.**

Three reasons, in order of how hard they are to argue with:

1. **What-if cannot be rendered.** Comparing scenarios takes 20–30 replications each (§6.2) over multi-week
   horizons. At 60 fps that is months of wall clock. The core must run headless in Node, at 1000× real time,
   with no WebGL.
2. **Live data cannot be owned by a renderer.** When a scanner event says bin `FM-03-018-C05` is now empty, the
   model must change and the scene must follow — not the other way round.
3. **Determinism is not testable through a renderer.** Same seed, same scenario, same answer — verified in CI,
   in Node, without a GPU.

### The split

| Layer | Owns | Imports | Runs |
|---|---|---|---|
| **Engine** `src/sim/engine/` | clock, event queue, resource pools, activities, random streams, statistics | nothing (no `three`, no DOM) | worker, node, browser |
| **Model** `src/sim/model/` | FC process graph, flow units, standards, routing graph, policies, KPI definitions, event vocabulary | engine | worker, node |
| **Bridge** `src/sim/view/` | subscribes to sim state/events, drives the existing scene modules | engine + model + `three` | browser |
| **Adapters** `src/adapters/` | live feeds → canonical events | engine vocabulary only | browser or node |

The engine is domain-free and reusable; the model is the FC. Keep the line between them honest — it is what
stops "the engine" from becoming an unbounded project.

### De-risking the refactor

This touches every scene module, so it does not happen in one commit. Strangler pattern:

1. Build the sim core beside the current loops, driven by the *existing* `update(dt)` calls (sim advances in
   `frame()`, nothing else changes). The twin keeps working the whole time.
2. Migrate one flow end to end — pick → takeaway → pack — so `people`, `conveyor` and `packing` read from the
   sim rather than owning state. Prove it, measure it.
3. Migrate the rest module by module, deleting each scripted loop as its view lands.
4. Only when the last loop is gone is the inversion done.

Two seams make this cheaper than it looks:

- **The actor driver is already queue-shaped.** `People.assign()` builds a `Step[]` per actor and `stepActor`
  consumes it; the only thing making it an infinite loop is `a.i = (a.i + 1) % a.steps.length`. Replacing where
  plans *come from* — work-driven and unbounded — while keeping the stepper, is the smallest viable change. The
  string-matching carry logic (`task.startsWith('Stowing')`) is the piece to replace with real load state.
- **`OrderTrace` is the working template.** It already resolves a real picker, a real pack station and a real
  sort lane out of the facility, moves along the real conveyor paths at a real speed, emits events and mutates
  `lane.units`. It is hardcoded to one item and one spur; generalising it to N orders *is* the order-flow
  engine in embryo.

## 4. The engine

### 4.1 Time and clock

A discrete-event clock, not a fixed step. The sim jumps from event to event; there is no work when nothing
happens, which is what makes multi-week horizons and 30 replications cheap.

- **Sim time** is authoritative, in integer milliseconds (fixed-point, so arithmetic is exactly reproducible).
- **View time** lags sim time and interpolates. A picker walking is an *activity* with a start and an end; the
  view lerps between them, so 60 fps smoothness and 1000× sim speed coexist.
- Controls: play, pause, step-one-event, speed (1× / 10× / 100× / max), and a timeline scrubber. Scrubbing
  backwards means restoring a snapshot (§4.10), not rewinding a renderer.

### 4.2 Event scheduler

A priority queue ordered by `(time, priority, sequence)`. The sequence tiebreak makes ordering total and
therefore reproducible — equal-timestamp events never resolve by insertion accident.

Event kinds: `arrive`, `task.start`, `task.end`, `resource.acquire`, `resource.release`, `move.start`,
`move.end`, `scan`, `state.change`, `metric.tick`, `shift.change`, `failure`, `custom`.

### 4.3 Flow units

The things that move. Each has an identity, a location, a state and a history — history is what makes an
order traceable (and lets the console's FOLLOW ORDER become a query rather than a special case).

`Order` → `OrderLine` → `Tote`/`Carton` → `Parcel` · `Pallet`/`LPN` · `Trailer` · `Return`

### 4.4 Resources, calendars, shifts

Anything with finite capacity: `Person(role)`, `Station`, `DockDoor`, `Vehicle`, `Cart`, `TotePool`,
`ConveyorSegment`, `Printer`, `StagingLane`, `Bin`/`PickFace` (an inventory location is a resource too).

Resources have calendars, not just counts: shift patterns, breaks, start-up meeting, overtime, absenteeism.
The current "60 associates on the floor" (`PLAN.md`) becomes a *shift plan* that scenarios can vary.

### 4.5 Process graph

The process flow already written in `PLAN.md` becomes the executable graph. Nodes are the real areas; edges
carry the flow and the routing rules.

```
INBOUND_ARRIVE → DOCK_ASSIGN → UNLOAD → RECEIVE_DECANT → QC ─┬→ PUTAWAY_STOW   → (bin/face)
                                                             └→ PUTAWAY_RESERVE → (pallet slot)
REPLENISH → PICK → [conveyor | walk-to-drop] → REBIN → PACK → SLAM → SORT → STAGE → LOAD → DEPART
RETURNS_RECEIVE → GRADE → { RESTOCK | REFURBISH | LIQUIDATE | DISPOSE }
DAMAGE → PROBLEM_SOLVE → ICQA
```

Both flow modes (`conveyor`, `walk`) stay first-class — they are a scenario parameter, and the twin already
switches between them at runtime already (the `#sel-flow` control in `src/main.ts`).

### 4.6 Travel and routing graph

Aisle-centreline graph over the hall, built from `src/layout.ts` (aisles, cross-aisles, the fast-mover 1.4 m
cart aisles, dock aprons). Travel time = shortest path ÷ speed, **with turn and congestion penalties**. When
travel is modelled rather than assumed, the sim can answer layout questions — which is half of what a
what-if study is for.

### 4.7 Standards — where the rates come from

The engine does not measure UPH and extrapolate; it derives throughput from **engineered standards**, which is
both more defensible and the industry direction of travel (UPH treats every task as equal and hides travel —
see ELS in [references](#references)).

| Standard | Composed of | Real anchor |
|---|---|---|
| Pick | travel + reach + scan + grasp + place, by face type (hand-stack, carton-flow, hopper bin) | manual pick 120–175 units/hr typical, 250+ best-in-class; e-comm 130–200 |
| Pack | box selection + pack + label, by single/multi | pack 100–150 UPH by order type |
| Receive / decant | unload + count, by load type (palletised vs floor-loaded) | unload 7–8 PPH palletised |
| Putaway / replenish | travel + lift + scan | derived from travel graph |
| Dock | leveler, restraint, seal, dwell | real appointment data |
| Learning curve | new-hire ramp | 60% week 1, 80% week 3, 100% week 5–6 |

Every one of these is a named, cited parameter in one file, editable, and shown in the UI with its source —
the same rule as the realism standard, applied to numbers instead of objects.

### 4.8 Randomness and determinism

- Seeded streams, **one per concern** (demand, pick times, travel variance, failures, absenteeism) — not one
  global stream. Independent streams mean changing the failure model does not shift every pick time.
- Built on `src/rng.ts`, extended to named forks: `rng.fork('demand')`.
- **The sim takes its own streams.** One global `mulberry32` stream is consumed today at build time *and* at
  runtime (pick loops, trace start), so drawing from it would shift phase-1 visuals and walk loops. The pattern
  to copy already exists — `Console` and its `history()` helper each keep a separate stream.
- **Common random numbers** across scenarios: baseline and variant use the same seeds, so the comparison is
  paired and the difference has far less noise. This is standard DES practice and it is what makes a 10-minute
  difference in dock-to-stock readable rather than drowned.
- **Determinism fingerprint**: hash of `(seed, scenario, event journal) → KPI set`. Golden fingerprints in CI,
  exactly like `__rngDraws()` today. If a refactor changes results, CI says so.

### 4.9 Event journal and the canonical event schema

One append-only, versioned event vocabulary — **and this is the keystone of the whole plan**: the sim and the
live adapters emit *the same events*. Everything downstream (metrics, console, replay, alerts, layers) is
source-agnostic and cannot tell whether it is watching a simulation or a real building.

```jsonc
{ "v": 1, "id": "evt_01H…", "ts": "2026-09-21T14:32:07.412Z", "sim_ms": null,
  "source": "SIM" | "WMS" | "SCANNER" | "PLC" | "LABOR" | "YMS",
  "type": "pick.confirmed", "entity": "FM-03-018-C05", "actor": "P-0142",
  "payload": { "qty": 1, "order": "O-88412" }, "idem": "scan:P-0142:…" }
```

Written as JSONL: replayable, diffable, and the artefact a scenario run leaves behind.

### 4.10 Snapshot, fork, serialization

Full serialise/restore of sim state (flow units, resources, queues, calendars, RNG stream positions).

Three things fall out of it, and all three are required features rather than nice-to-haves:
**fork from live** (§6.5), **scrub the timeline** backwards (§4.1), and **regression tests** (§8).

## 5. Metrics engine

KPI definitions live in code next to the model, computed from the event journal and time-bucketed (minute →
hour → shift → day). Each carries: value, unit, window, comparison, and — when it comes from replications —
a confidence interval.

| Family | KPIs | Real anchor |
|---|---|---|
| Throughput | units/hr, lines/hr, orders/hr — overall and by zone, carrier, shift | against shift target |
| Flow | **dock-to-stock**, order cycle time, pick-to-ship, dwell by station | dock-to-stock best-in-class < 3.5 h |
| Labour | UPH by role, utilisation, indirect %, units per labour hour, overtime hours, cost/unit | ELS-derived, not measured-and-averaged |
| Quality | pick accuracy, damage rate, QC reject %, DPMO | best-in-class 99.68%+ |
| Service | on-time to carrier cutoff, OTIF, fill rate, backlog, **age of oldest order** | 98–99% on-time |
| Capacity | dock door, conveyor, pack station, staging lane utilisation; cube/space; tote pool | the console's `— of 62 doors` |
| Cost | labour cost per unit / per order / per line | |

**Continuous invariants** — checked every run, not sampled:

- **Conservation:** units in = units out + WIP + scrap + damage. Always.
- **Little's Law:** WIP = throughput × cycle time, within tolerance. Catches whole classes of modelling error.
- **Causality:** no effect before its cause; no resource double-allocated; no negative inventory.

A run that violates an invariant fails loudly rather than producing a plausible-looking KPI.

## 6. What-if scenarios

### 6.1 Scenario schema

A scenario is **a baseline plus a delta** — never a copy of the world. Small, reviewable, diffable, and it
survives changes to the baseline underneath it.

```jsonc
{ "id": "peak-staffing", "extends": "baseline-real-fc",
  "horizon": "7d", "warmup": "8h", "reps": 20, "seeds": [1001, 1002, …],
  "demand":   { "orders": "peak-week.json", "profile": "monday-peak", "cutoff": "16:00" },
  "labour":   { "picker": 42, "packer": 24, "receiver": 16, "absenteeism": 0.06 },
  "layout":   { "fm1Bays": 20, "packStations": 60 },
  "equipment":{ "reachTruck": 6, "cart": 46 },
  "policy":   { "waveRelease": "waved", "pickPath": "serpentine",
                "replenTrigger": { "min": 0.25, "max": 0.6 } },
  "disruption":[{ "at": "3d 06:00", "type": "conveyor.down", "target": "TAKEAWAY-1", "for": "45m" }] }
```

Seven lever families — demand, labour, layout, equipment, policy, shift, disruption. Every lever traceable to
a `PLAN.md` decision, so the scenario space is the facility you actually approved.

### 6.2 The runner (this is where credibility is won or lost)

Running a scenario naively and reporting one number is how simulation gets a bad name. The runner does it
properly, with defaults that are right rather than convenient:

| Concern | Approach | Source |
|---|---|---|
| Warm-up | Remove initialisation bias by a stated method (Welch's graphical procedure), per scenario — an empty FC is not steady state | Law & Kelton |
| Replications | N reps with different seeds until the CI half-width is under a target relative error (default 5%, 95% CI) — typically 10–30 | replication/deletion |
| Comparison | Paired: common random numbers across scenarios, paired-t on the difference | variance reduction |
| Reporting | Never a bare mean. Mean + CI + n, and the distribution, not just the centre | |

A scenario that cannot reach its target error in a sane number of replications says so, rather than quietly
reporting a noisy number.

### 6.3 Experiment design

- **One-factor sweeps** — the common case: vary one lever across a range, plot the response curve.
- **Factorial / fractional-factorial** — when levers interact (staffing × demand × conveyor speed).
- **Parameter search** — grid first, then a simple search (Bayesian or GA) for a target: "cheapest staffing
  that holds 99% on-time at peak".
- **Sensitivity / tornado** — which lever actually moves the KPI. Usually the answer is not the one assumed,
  which is the entire value of doing this.

### 6.4 Comparison UX

In the console, on top of the existing KPI tile and event stream surfaces:

- **Run controls**: play / pause / step / speed / scrub (the `FEED · LIVE 1.0s` slot becomes the run clock).
- **Scenario panel**: the seven lever families as typed controls, with each parameter's source and default.
- **Compare view**: baseline vs variants side by side — KPI deltas with CI bands, small multiples of time
  series, and a tornado of lever sensitivity.
- **Explain this number**: click any KPI, get the events that produced it. Metrics are derived from the
  journal, so this is a query, not a rebuild. It is also the fastest way to catch a modelling bug.
- **Scenario library**: save, name, version; share by deep link (`#scenario=…&rep=3&t=14:32`).

### 6.5 Cold start vs fork from live

| Mode | Starts from | Answers |
|---|---|---|
| **Cold start** (design-time) | Empty or standard opening state, warm-up removed | Capacity, layout, staffing envelope, policy choice |
| **Fork from live** (operational) | A snapshot of the live twin's current state | "Given exactly where we are now, what happens if…" |

Fork-from-live is short-horizon and operational — it inherits the real WIP, the real queue ages, the real
trailer on door 14 — so it needs no warm-up and returns in seconds. This is the mode that earns its keep on a
Tuesday afternoon, and the reason §4.10 exists.

## 7. Live data

### 7.1 Framing — ISO 23247

The live half of this plan maps cleanly onto ISO 23247's four domains, which is worth using deliberately so
that the architecture is a known shape rather than an invention:

| ISO 23247 domain | Here |
|---|---|
| **Observable** | The real FC: WMS/WES, scanners, conveyor PLCs, labour system, yard, carriers |
| **Data collection & device control** | `src/adapters/` — REST/WS, MQTT, OPC UA, file drop. Read-only. |
| **Core** | `src/sim/` — the model, the sim, metrics, scenario engine |
| **User** | The console, the 3D twin, dashboards |

### 7.2 Feed modes

| Mode | What it does | Why |
|---|---|---|
| **Replay** | Recorded journal plays through the same path as live | Build and test the whole pipeline before any real feed exists |
| **Mirror** | Live feed drives the twin; sim is off | The live twin |
| **Hybrid** | Live feed sets the state, sim runs forward from it | Fork-from-live and short-horizon prediction |

Bootstrap note worth acting on: **the sim is the test fixture for the live pipeline.** It already emits a
realistic canonical event stream (§4.9), so the adapters, mapping, reconciliation and console can be built,
tested and demoed at full scale before a single real integration exists. That removes the usual
"we'll test it when we have data" dead end.

### 7.3 The mapping layer — the actual hard part

Transport is a solved problem; mapping is where digital twin projects die (IDC attributes ~73% of failures to
data quality and integration). So the mapping gets first-class treatment:

- A declarative **mapping spec**: source field/event → twin entity + attribute, versioned in the repo.
- **ID reconciliation**: the twin's location IDs (`RA-07-012`, `FM-03-018-C05`, `OB-15`) against the WMS's
  own scheme; SKU and carrier mapping; an explicit unknown/unmapped queue rather than silent drops.
- **Contract tests** per source, run against captured fixtures, so a WMS update breaks CI before it breaks the
  twin.
- **A mapping inspector** in the console: what came in, what it mapped to, what it could not.

### 7.4 Ingest pipeline

`buffer → validate → dedupe → order → apply → reconcile`

- **Idempotency** by key — scanner events duplicate, and a duplicate must not double-count a pick.
- **Late and out-of-order events**: event-time processing with a watermark and a lateness window; a scan that
  arrives 40 s late lands in the right place in history, not appended at the end.
- **Backpressure**: the feed can burst; the twin drops render fidelity before it drops events.
- **Latency classes**: control-flow (sub-100 ms), operational telemetry (100 ms–5 s), accounting/reconciliation
  (seconds–minutes) — each with its own path and expectations.

### 7.5 Reconciliation and drift

A twin that silently diverges from reality is worse than no twin. So:

- Periodic **snapshot reconciliation** against the WMS (inventory on hand, open orders, dock state).
- A **divergence report** — where the twin and the system of record disagree, by entity.
- **Drift correction** with a visible, logged adjustment event. Never a silent overwrite.
- Feed **health on the console**: lag, event rate, schema errors, unmapped entities, last-good timestamp. The
  existing `FEED · LIVE 1.0s` chip becomes the truth of whether the twin is actually connected.

### 7.6 Security

Read-only credentials and network path by default; no PII in the event journal; secrets never in the client
bundle (an adapter service holds them); every reconciliation adjustment audited. Safety functions stay in the
PLC where they belong — the twin never writes to the physical system.

## 8. Validity standard (hard rule)

`PLAN.md` has a realism standard: *nothing unreal ships*, with a real reference for every object. The
simulation needs its twin rule, or it will produce confident nonsense:

1. **Every rate has a real reference.** Each parameter cites a published benchmark, a measured value, or a
   stated assumption — visible in the UI, not buried in code.
2. **No bare averages.** Any KPI from replications comes with a confidence interval and its replication count.
3. **Warm-up is removed by a stated method** (Welch's), per scenario, not by hoping eight hours was enough.
4. **Comparisons are paired** — common random numbers, paired-t on the difference.
5. **Invariants hold every run** — conservation, Little's Law, causality. Failure is loud.
6. **Face validity per run** — a run whose flow does not match the `PLAN.md` process diagram is a bug, not a
   finding. A visual replay of the run is part of the check.
7. **The reference bar.** If it would not survive review in a real FC design study, it does not pass here.

## 9. Milestones

`PLAN.md` reserves milestones 14–16 for order flow and 17–18 for the live twin. What-if scenarios turn out to
be a deliverable in their own right rather than a side effect of order flow, so this plan refines that into
six milestones, 14–19. `PLAN.md`'s phase table needs a one-line update to match.

Sizes: **S** under an hour · **M** a few hours · **L** a day or more. All **TODO**.

## 10. Execution and performance

| Question | Answer |
|---|---|
| Language | TypeScript for the core. DES at this scale is cheap — a busy day is ~10⁵–10⁶ events; a 30-rep, 7-day study is seconds to minutes. |
| Where it runs | Web Worker for interactive runs; Node for batch studies and CI. Same code. |
| Do we need WASM/Rust? | Not to start. Only revisit if batch studies of the full scenario space stop fitting in a coffee break. |
| Render budget | 60 fps with 60+ animated associates driven by the sim is the real risk, not the sim maths — LOD/instancing in 12.3. |
| Persistence | Journals and results as files (JSONL/JSON); snapshots for fork. No database until something actually needs one. |
| Deployment | The twin stays static (12.4). A live feed needs one small adapter service to hold credentials; scenario batch runs are local or CI. |

## 11. Risks

| Risk | Why it bites | Mitigation |
|---|---|---|
| **The inversion refactor** | Touches every scene module; the twin could be broken for weeks | Strangler pattern (§3); twin works at every commit; migrate one flow first |
| **Baked geometry** | The scene is built once and never repainted, so a sim state change has no way to appear on screen | Explicit diff/repaint path before any migration (15.10); `Racking.setLayer('inventory')` is the working precedent |
| **Calibration data** | Without real numbers it is a plausible cartoon | Public benchmarks + every parameter named, cited and tunable (§4.7); validation report (16.5) |
| **Scope creep into a product** | "Simulation engine" can mean anything | Engine/model split (§3); the FC is the only model until it is validated |
| **Live feed does not exist yet** | Blocks the whole live half | Sim-as-test-fixture (§7.2) + replay; build the pipeline before the integration |
| **Silent drift** | A wrong twin is worse than none | Reconciliation + divergence report + honest feed health (§7.5) |
| **False confidence from noisy runs** | One rep, one number, big decision | Replications + CIs + paired comparison as defaults, not options (§6.2) |
| **Determinism erosion** | Every later bug becomes unreproducible | Integer-ms time, ordered ties, fingerprint CI (§4.8) |

## 12. Decisions needed from you

These change the plan materially, so they should be settled before milestone 17 rather than during it.

1. **Is there a real feed to target?** A named WMS/WES, or aspirational? This sets whether 18.3–18.5 are
   built against a real system, a spec, or only fixtures.
2. **Who are "people" creating scenarios?** You alone, a planning team, or customers? It decides whether the
   studio is a power tool or needs guard-rails, presets and plain-language output.
3. **Design-time or operational emphasis?** Cold-start studies (capex, layout) and fork-from-live (this
   afternoon) are the same engine but different UX priorities. Which earns its keep first?
4. **Is a cost model in scope?** Labour cost per unit turns "faster" into "worth it", but needs wage and
   overhead inputs.
5. **One FC or a network?** The engine allows multi-site later; the plan assumes one building until told
   otherwise.
6. **Does anything write back?** This plan says read-only, always. Confirm, because it is the one decision
   that changes the safety and security story completely.

## 13. Assumptions

- The facility, layout and process flow in `PLAN.md` are the model. This plan adds dynamics, not a new FC.
- Phase 1 continues in parallel; the sim builds beside it and takes over module by module.
- Fictional-but-plausible facility data stays; only *rates* need real anchors.
- Read-only integration, no write-back, no PII in journals.
